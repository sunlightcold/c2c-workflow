# 代付机器人功能对齐

## 目标

在现有 PostgreSQL、NestJS、多所属单位与商家隔离模型上，对齐 `pfa-pay` 代付机器人的用户可见能力与交互语义。参考实现只用于确认业务行为，不复制 MongoDB 模型、明文凭据或单进程机器人结构。

## 命令与自然语言入口

| 能力     | 命令                 | 中文入口                           |
| -------- | -------------------- | ---------------------------------- |
| 帮助     | `/help`、`/start`    | -                                  |
| 用户编号 | `/myid`              | -                                  |
| 查单     | `/query 标识`        | `查单 标识`                        |
| 回单     | `/receipt 标识`      | `回单 标识`                        |
| 今日统计 | `/stats`             | `今日跑量`、`今日统计`             |
| 提交批次 | `/submitbatch`       | `提交`、`提交批次`、`提交批次订单` |
| C2C 申诉 | `/appeal C2C订单号`  | `申诉 C2C订单号`                   |
| C2C 日报 | -                    | `日报`、`日报 YYYYMMDD`            |
| 状态     | `/status`            | -                                  |
| 手工代付 | 四行一笔，可连续多笔 | 商户订单号、金额、姓名、支付宝账号 |

命令允许 Telegram 的 `@botname` 后缀。未授权能力不得因中文别名或回调绕过最终鉴权。

四行手工代付和未提交订单作废统一由“支付宝批量支付”能力控制，“提交支付批次”仅控制批次提交。
手工代付与 C2C 买币支付使用同一套支付方案路由，订单来源仅记录为 `BOT_MANUAL` 或 `C2C_BUY`，
不参与支付账号、通道或批次策略选择。群组的通知场景不参与手工订单批次筛选，避免 C2C 通知群无法
提交机器人手工订单。

C2C 申诉复用统一的平台申诉流程：机器人先实时校验币安或欧易订单；存在默认原因码 `1` 时直接提交，否则创建一次性原因选择按钮。提交阶段自动通过支付通道回单能力获取 PDF 并转换为 JPG。币安按预签名地址上传后提交；欧易先上传一张 JPG 回单，再使用返回的图片地址提交申诉，不要求用户人工上传付款回单。原因按钮回调必须重新鉴权并校验租户、商家和交互上下文。

## 查单契约

- 在当前所属单位与商家范围内，支付订单依次支持系统支付单号、商户订单号、支付平台流水号与内部订单 ID 查询。
- 未找到支付订单时，再按系统批次号、支付平台批次流水号与内部批次 ID 查询支付批次。
- 支付订单使用与 `pfa-pay` 一致的信息分组、状态图标和 HTML 安全转义。
- 成功订单且调用人拥有回单权限时显示“获取回单”；点击后按支付宝批次明细 ID 申请并轮询电子回单，下载支付宝 PDF 并转换为最多 5 页 JPEG，随后由机器人直接发送图片到当前群组。不得向群组暴露临时 PDF 地址；失败或超时必须显示真实结果，禁止仅凭支付宝流水号宣称回单已生成。
- 未提交资金请求的订单且调用人拥有支付宝批量支付权限时显示“作废订单”。
- 支付批次显示逐笔明细，每页八笔；翻页回调重新执行最终鉴权和商家范围校验。
- 不存在时统一返回“未查询到订单或批次”，禁止泄露其它所属单位或商家的订单是否存在。

## 失败与幂等语义

- 所有查询与按钮操作同时约束 `tenantId` 和 `merchantId`。
- 已启用的机器人遇到 Telegram 连接或长轮询异常时保持运行状态，按 5 秒起步、最高 60 秒的指数退避持续重连；成功完成一次长轮询后恢复为 5 秒。只有人工停止、配置停用或应用关闭才能终止运行时。
- 作废操作仅允许尚未提交资金请求的支付订单；已经提交的批次或订单返回冲突，不得修改资金状态。
- 回调重复点击必须返回已处理或当前状态不允许，不得重复提交资金请求或申诉。
- 用户输入与上游错误必须进行 HTML 转义；Telegram 消息中不得出现凭据、Token 或完整上游请求。
- 批次和单笔结果通知保持一次性投递语义，批次子订单不重复发送单笔最终结果。
- 自动发现和创建支付订单的任务允许按候选状态继续执行，但同一所属单位、商家、错误码和关联单号的异常通知只投递一次；去重记录必须持久化，不能依赖单进程内存状态。
- 支付通道已经返回成功后，平台标记付款使用独立状态 `PENDING / PROCESSING / FAILED / SUCCESS`。标记失败必须停在 `FAILED`，15 秒恢复任务不得自动重复调用标记付款接口。
- 平台确认由数据库条件更新原子认领；同一订单只能有一个 Worker 执行。OKX 按商家账号使用持久化锁和 `paidConfirmIntervalMinMs / paidConfirmIntervalMaxMs` 串行节流，Binance 不受该节流影响。
- 标记付款失败通知使用与 `pfa-pay` 一致的“⚠️ C2C 确认付款失败”样式并提供“重试”按钮。按钮回调重新鉴权，人工重试先查询平台；已付款直接收口，平台仍待付款时才重新标记，且绝不重新提交支付宝付款。
- 15 秒恢复任务继续回查支付宝处理中或结果未知的订单；平台确认只接管未认领的 `PENDING` 或超时的 `PROCESSING`，超时恢复只查询平台状态，不盲目重复标记。
- 自动批次先发送“自动批次提交结果”并保存每个群组的 Telegram 消息编号；最终“自动批次处理结果”按群组回复对应的提交消息，避免结果先于提交摘要或跨群串联。
- 支付订单资金成功后始终显示“支付成功”；平台标记付款使用独立状态并单独显示“待确认 / 确认中 / 确认失败 / 确认成功”。历史 `PLATFORM_CONFIRM_PENDING / COMPLETED` 仅用于迁移兼容，不再生成；收款方式使用“支付宝/银行卡/微信支付”中文映射。

本项目明确不实现 `pfa-pay` 的余额查询能力；相关 `/balance`、`余额` 和 `查询余额` 入口不注册，避免把支付账号余额误当成代付机器人业务能力。
机器人和群组恢复独立的 `C2C_PAID_NOTIFICATION`（C2C 标记付款通知）能力。开启时发送完整批次标记付款结果；关闭且全部成功时静默；关闭但存在失败时仍发送失败摘要和重试按钮。单笔标记付款失败同样强制通知，避免关闭普通结果通知后吞掉需要人工处理的异常。全局“启用业务通知”关闭时仍保持静默。能力列表不暴露余额查询、重复的手工支付和群成员管理等无效开关。

## 验收

- 命令解析、查询范围、查单按钮、批次分页、中文入口、权限拒绝、重复回调均有单元测试。
- 后端 lint、typecheck、相关 Jest 测试通过。
- 本任务不进行页面自动化验证。
