# C2C 运营管理平台业务需求说明书

> 文档版本：V3.3
> 文档状态：业务修订稿
> 更新日期：2026-09-11
> 本期业务：币安、欧易 C2C 买币付款及机器人支付

## 一、系统业务结构

### 1.1 总体结构

总部在系统中同时承担两类业务：

1. **平台管理**：管理全部代理商、用户权限、支付通道、自动任务、操作记录和系统参数。
2. **总部自营**：直接经营总部自己的商家、订单、支付账号、支付业务和支付机器人群组。

总部自营与代理商使用同一套业务功能。系统统一使用“所属单位”表示一笔业务属于总部自营还是某个代理商。

本期只开放 C2C 买币付款，不获取、不展示也不处理卖币订单。系统保留订单方向、平台原始状态和平台能力扩展位置，后续接入卖币时单独增加收款核对、放币和争议处理流程，不改变现有买币付款流程。

```text
总部平台
├── 平台管理
│   ├── 所属单位管理
│   ├── 用户与角色管理
│   ├── 支付通道配置
│   ├── 自动任务管理
│   ├── 操作记录
│   └── 系统参数
│
├── 总部自营
│   ├── 商家、订单、支付账号、支付业务
│   └── 支付机器人、群组和群成员
│
└── 代理商
    ├── 代理商 A：商家、订单、支付账号、支付业务、支付机器人
    ├── 代理商 B：商家、订单、支付账号、支付业务、支付机器人
    └── ……
```

### 1.2 主要业务对象

| 业务对象   | 业务说明                                                                                |
| ---------- | --------------------------------------------------------------------------------------- |
| 所属单位   | 一组业务数据的归属方，可以是“总部自营”或某个代理商                                      |
| 代理商     | 由总部管理、独立开展业务的经营单位                                                      |
| 商家       | 所属单位名下的一个 C2C 经营账号，只能经营币安或欧易其中一个平台                         |
| 商家订单   | 本期从商家所选平台获取的 C2C 买币订单；订单方向保留卖币扩展能力                         |
| 支付账号   | 所属单位用于付款或退款的支付宝、微信等资金账号                                          |
| 支付通道   | 支付账号已经开通的一种具体支付能力                                                      |
| 支付方案   | 商家可使用的支付规则，明确业务场景、收款方式、支付账号、支付通道和使用顺序              |
| 支付订单   | 根据 C2C 买币订单或机器人手工指令产生的一笔付款业务，或者根据退款申请产生的一笔退款业务 |
| 批量付款   | 将多笔符合条件的支付订单合并处理的一次付款业务                                          |
| 支付机器人 | 在已绑定的商家群中创建支付订单、提交批次、查询业务并反馈处理结果的机器人                |

### 1.3 核心业务关系

1. 系统预设“总部自营”所属单位，总部可以在该单位下直接开展全部经营业务。
2. 总部可以新建多个代理商，每个代理商作为一个独立的所属单位开展业务。
3. 每个商家只属于一个所属单位，不能同时属于总部自营和代理商。
4. 每个商家只能选择一个交易平台：币安或欧易，不能同时绑定两个平台。
5. 同一经营主体如果同时经营币安和欧易，需要分别创建两个商家。
6. 商家创建后不能更换交易平台；如需更换，应停用原商家并重新创建。
7. 一个所属单位可以创建多个支付账号，一个支付账号可以开通多个支付通道。
8. 商家通过“支付方案”使用支付账号和支付通道；一条支付方案必须同时指定一个支付账号和该账号下的一个支付通道。
9. 一个商家可以配置多条支付方案，分别用于不同业务场景、收款方式、金额范围和执行方式。
10. 商家只能使用本所属单位的支付账号，不能使用总部自营或其他代理商的支付资源。
11. 一个所属单位可以创建多个支付机器人，一个机器人可以绑定多个本单位商家群组。
12. 每个群组只绑定一个商家并指定群内支付场景；系统只能从该商家匹配该场景的支付方案中选择。
13. 商家、订单、支付账号、支付订单、机器人和群组都必须有明确的所属单位。
14. 支付订单来源分为“C2C 买币订单”“机器人手工支付”和“退款申请”；各类来源分别记录原业务编号，并按所属单位、商家、来源和原业务编号防止重复创建。退款申请同时关联原成功支付订单。
15. 本期卖币能力保持关闭，卖币订单不会进入订单列表、支付流程、机器人操作或自动任务。

## 二、角色与数据范围

| 角色         | 可查看的数据                 | 主要操作范围                                   |
| ------------ | ---------------------------- | ---------------------------------------------- |
| 总部管理员   | 全部所属单位的全部数据       | 管理代理商、总部自营业务、用户权限和全局设置   |
| 总部运营     | 总部自营及被授权的代理商数据 | 管理商家、订单、异常和支付机器人               |
| 总部财务     | 总部自营及被授权的代理商数据 | 管理支付账号、支付订单、批量付款和对账         |
| 总部审计     | 被授权范围内的数据           | 查看业务记录、对账结果和操作记录               |
| 代理商管理员 | 本代理商全部数据             | 管理本代理商用户及全部经营业务                 |
| 代理商运营   | 本代理商或指定商家数据       | 管理商家订单、异常和支付机器人                 |
| 代理商财务   | 本代理商或指定商家数据       | 管理支付账号、支付订单、批量付款和对账         |
| 商家管理员   | 被授权的商家数据             | 管理指定商家的资料、订单、支付绑定和机器人群组 |

数据查看规则如下：

1. 总部管理员可以查看和管理全部所属单位，也可以直接经营总部自营业务。
2. 总部其他人员按授权查看总部自营或指定代理商的数据。
3. 代理商人员登录后只看到本代理商的数据，系统自动确定所属单位。
4. 商家人员只看到被授权商家的数据。
5. 总部页面显示“所属单位”筛选项和列表字段；代理商页面无需反复选择所属单位。

## 三、系统菜单

系统使用概览、商家管理、支付管理、机器人管理和系统管理等一级菜单，一级菜单展开后显示对应的二级菜单。总部与代理商使用同一套菜单结构，系统根据用户权限显示其可以使用的二级菜单。

| 一级菜单   | 二级菜单     | 主要功能                                                     |
| ---------- | ------------ | ------------------------------------------------------------ |
| 概览       | 工作台       | 查看订单、支付、商家连接和异常事项的整体情况                 |
| 商家管理   | 所属单位     | 管理总部自营和代理商资料及状态                               |
| 商家管理   | 商家账号     | 新建和管理商家账号，设置交易平台、支付方案和机器人群组       |
| 商家管理   | 商家订单     | 查询买币订单及订单详情，执行同步、支付、确认和申诉操作       |
| 支付管理   | 支付账号     | 管理本所属单位的支付账号及各账号已开通的支付通道             |
| 支付管理   | 批次策略     | 管理支付批次的手动、时间间隔和订单数量提交规则               |
| 支付管理   | 支付订单     | 管理 C2C 支付、机器人支付和退款业务                          |
| 支付管理   | 支付批次     | 将多笔支付订单组批、提交并查询处理结果                       |
| 机器人管理 | 机器人实例   | 创建和管理支付机器人，设置默认功能、确认方式和运行状态       |
| 机器人管理 | 群组绑定     | 将群组绑定到商家，设置支付场景、下单开关、可用功能和单笔限额 |
| 机器人管理 | 群组成员     | 管理群成员角色及可执行的支付、查询和批次权限                 |
| 机器人管理 | 超级管理员   | 管理全平台或指定机器人的超级管理员，授权其绑定商家群组       |
| 系统管理   | 用户与角色   | 管理后台用户、角色及可操作的商家范围                         |
| 系统管理   | 支付通道配置 | 管理全平台可使用的支付方式和通道                             |
| 系统管理   | 自动任务     | 查看订单获取、支付查询、对账和通知任务                       |
| 系统管理   | 操作记录     | 查询重要业务操作和人工处理记录                               |
| 系统管理   | 系统参数     | 管理平台公共业务参数                                         |

菜单使用规则如下：

1. 系统最多使用两级侧边菜单，不再继续拆分三级菜单。
2. 二级菜单对应独立工作页面；页面内的资料、记录和设置使用页签展示。
3. 总部管理员可以看到全部二级菜单；总部其他人员和代理商人员只看到已授权菜单。
4. “所属单位”和系统级配置只对总部开放。
5. 代理商在“系统管理”中主要使用“用户与角色”“自动任务”和“操作记录”。
6. 商家连接状态是独立的查看与处理页面，但一个商家仍只能连接币安或欧易其中一个平台，不能在此增加第二个平台。
7. 商家支付方案在“商家详情－支付设置”中维护，不另设复杂的路由菜单；实际选中的支付账号和通道在支付订单详情中查看。
8. 商家详情、订单详情、支付详情和群组详情从对应列表进入，不重复设置侧边菜单。
9. 机器人通知结果跟随原订单或批次展示，不单独设置“通知记录”菜单；发送异常统一进入工作台待办和操作记录。

## 四、功能模块

### 4.1 工作台

- 展示今日及指定时间范围的买币订单数量、买币金额、支付金额和完成情况。
- 分别展示总部自营、各代理商及各商家的经营数据。
- 展示待审核支付、待付款订单、结果未知支付、对账差异等待办事项。
- 展示商家连接异常、支付账号异常、订单同步异常和通知失败提醒。
- 总部可以按所属单位查看汇总；代理商只查看本单位汇总。
- 点击数据或待办可直接进入对应业务页面。

### 4.2 商家

- 新增、编辑、启用、暂停、停用和归档商家。
- 总部新建商家时可以选择所属单位，默认选择“总部自营”；代理商新建时自动归属本代理商。
- 新建商家时填写名称、编码、联系人、结算币种和经营资料。
- 新建时必须选择币安或欧易，且只能选择一个。
- 根据所选平台填写对应的商家账号和连接资料，并检查连接是否正常。
- 商家详情统一展示基本资料、所属单位、交易平台、连接状态、订单概况、支付设置和机器人群组绑定。
- “支付设置”中为商家配置支付方案，每条方案选择本单位的一个支付账号和该账号已经开通的一个支付通道。
- 支付方案可分别用于 C2C 自动付款、机器人付款或退款，并设置收款方式、即时或批量、适用金额、主用或备用顺序。
- 每组相同的业务场景、收款方式、执行方式和金额范围至少设置一条主用方案；多条主用方案按分配比例使用，还可以设置备用方案。
- 支持暂停和恢复订单获取；连接失效时在商家页面提示处理。
- 商家停用后不再获取新订单，也不再产生新的自动支付，历史数据继续保留。

### 4.3 订单

- 根据商家所选平台自动获取币安或欧易 C2C 买币订单及状态变化。
- 支持按所属单位、商家、平台、订单号、币种、金额、状态和时间查询。
- 总部可以查询全部所属单位；代理商只能查询本单位。
- 订单详情展示交易信息、付款信息、当前进度、关联支付、通知记录和处理记录。
- 支持单笔重新获取和按时间范围补充获取订单。
- 同一商家的同一平台订单只保留一笔，不因重复获取产生重复订单。
- 对超时、争议、状态不一致和获取失败的订单进行标记，并进入待办处理。
- 支持对订单添加处理说明、重新检查状态、转交处理和关闭异常。

### 4.4 支付

#### 支付订单

- 根据 C2C 买币订单创建付款或退款业务，也可以根据机器人四行支付信息创建手工支付业务。
- 支付订单必须记录来源类型和原业务编号；同一来源业务重复点击或重复处理只返回原支付订单。
- 创建前检查来源业务状态、金额、币种、收款方式、执行方式和是否已经支付。
- 系统从商家的支付方案中选择一条可用方案，并锁定具体的支付账号和支付通道。
- 支持审核、提交、暂停、取消、查询结果和处理异常。
- 每笔支付记录所使用的支付方案、支付账号、支付通道、选择原因、处理结果和处理时间。
- 支付结果暂时无法确认时标记为“结果未知”，继续占用额度；确认原付款结果前不得再次付款。
- 通道查询长期无法确认时，通过支付账单核对；账单仍无法确认时由财务提交凭证并经另一名有权限人员审核后确认最终结果。

#### 批量付款

- 只将同一所属单位、同一商家、同一支付账号、同一支付通道和同一币种下的多笔支付订单合并处理。
- 支持人工选择或按预设条件自动生成批次。
- 批次提交前核对总笔数、总金额、每笔订单状态、付款截止时间、账号及通道可用性和额度。
- 展示成功、失败、处理中和结果未知的明细。
- 仍有明细正在处理或结果未知时，批次保持“处理中”或“结果未知”；全部明细已有最终结果后，才可以判定全部成功、部分成功或全部失败。
- 部分成功时保留成功结果，只处理明确失败且允许重新付款的明细。

#### 支付账号

- 总部可以创建和管理总部自营支付账号；代理商可以创建和管理本代理商支付账号。
- 支持支付宝、微信、银行卡等支付账号，并为每个账号维护已经开通的支付通道。
- 一个支付账号只能保存一套当前有效的账号凭据，不提供多套凭据、凭据列表或凭据切换；更新时整套覆盖原凭据。
- 支付账号的 API 网关地址可自定义，可配置支付宝官方地址、代理网关或本地 Mock 地址，不使用固定环境选项限制域名。
- 支付宝账号支持公钥模式和证书模式。公钥模式配置应用 ID、应用私钥和支付宝公钥；证书模式配置应用 ID、应用私钥、应用公钥证书、支付宝公钥证书和支付宝根证书。密钥和证书通过选择本地文件读取保存，保存后不再显示原内容。
- 一个支付账号可以同时开通多种支付通道，例如单笔转账和批量转账；通道必须属于该支付账号，不能混用其他账号的通道。
- 同一支付账号下的所有支付通道共用该账号唯一凭据；通道只配置能力开关、金额范围、并发限制和运行状态，不单独配置账号凭据。
- 支付账号维护可用余额、单笔限额、每日限额和使用时段；支付通道维护收款方式、即时或批量、金额范围和运行状态。
- 商家支付方案维护业务场景、收款方式、支付账号、支付通道、主备顺序和同顺序下的分配比例。
- 支持启用、暂停和停用；停用后不再接收新业务，已提交业务继续查询最终结果。
- 同一支付账号及其通道可以被本单位多个商家使用，但每个商家都必须单独配置支付方案和使用额度。

#### 支付方案选择规则

以下规则用于系统主动付款或退款。后续卖币业务的收款核对不使用本选择规则，届时使用独立的到账匹配流程。

系统按以下顺序为主动付款或退款订单选择支付账号和支付通道：

1. **确定订单要求**：读取所属单位、商家、业务场景、付款或退款方向、收款方式、即时或批量、币种和金额。
2. **查找商家方案**：只查找该商家已经启用的支付方案，不使用未授权给该商家的账号和通道。
3. **匹配收款方式**：支付宝收款只匹配支付宝通道，微信收款只匹配微信通道，银行卡收款只匹配银行卡通道。
4. **匹配执行方式**：需要即时付款的订单不能进入批量通道；批量订单只能使用支持批量处理的通道。
5. **检查可用条件**：支付账号和通道均为正常状态，金额在允许范围内，账号余额、账号总额度、商家使用额度、使用时段和处理能力均满足要求。
6. **选择主备方案**：优先使用主用方案；主用不可用时按备用顺序选择。同一顺序有多条方案时，按设置的分配比例选择。
7. **锁定支付组合**：选中后，支付订单固定记录“支付账号 + 支付通道”，同时占用账号总额度和商家使用额度，提交过程中不得随意更换。
8. **无可用方案**：支付订单进入“待配置”，说明不匹配原因。运营人员补充或恢复方案后执行“重新匹配”，匹配成功后按审核规则进入“待审核”或“待提交”。
9. **提交前复核**：正式提交前再次检查来源业务、收款资料、付款截止时间、操作权限、账号状态、通道状态、余额和额度；任一条件变化时停止提交并进入相应待办。

支付方案示例如下：

| 业务场景     | 收款方式 | 执行方式 | 适用金额     | 支付账号     | 支付通道   | 使用顺序 |
| ------------ | -------- | -------- | ------------ | ------------ | ---------- | -------- |
| C2C 自动付款 | 支付宝   | 即时     | 0－10,000 元 | 支付宝账号 A | 单笔转账   | 主用     |
| C2C 自动付款 | 支付宝   | 即时     | 0－10,000 元 | 支付宝账号 B | 单笔转账   | 备用 1   |
| 机器人付款   | 支付宝   | 批量     | 0－50,000 元 | 支付宝账号 A | 批量转账   | 主用     |
| 退款         | 银行卡   | 即时     | 0－20,000 元 | 银行账号 C   | 银行卡转账 | 主用     |

例如，一笔 8,000 元的 C2C 支付宝即时付款订单，先使用“支付宝账号 A + 单笔转账”；账号 A 不可用时再使用“支付宝账号 B + 单笔转账”。该订单不能使用账号 A 的批量转账通道，也不能使用银行卡通道。

支付方案切换规则如下：

1. 尚未向支付通道提交时，如果选中的账号或通道失效，系统可以释放原额度并选择下一条备用方案。
2. 支付通道明确返回“未受理、未扣款”时，可以重新检查后选择备用方案再次提交。
3. 支付通道已经受理、正在处理或结果未知时，只能继续查询原支付结果，不能切换账号或通道再次付款。
4. 每次重新选择都形成新的支付尝试，但仍属于同一笔支付订单；历史选择和失败原因全部保留。
5. 有权限人员可以在提交前从符合条件的方案中人工指定一条，不能选择不匹配收款方式、金额或执行方式的方案。
6. 支付方案修改、停用或调序不自动改变已经锁定订单的方案快照；未提交订单仍须复核账号和通道状态，已提交订单继续按原账号和通道查询结果。
7. 审核等待期间账号、通道、余额或额度发生变化时，审核通过不代表可以直接付款，正式提交前仍须重新检查。

#### 对账

- 按支付账号获取账单，与系统支付订单进行核对。
- 识别系统有记录但账单无记录、账单有记录但系统无记录、金额不一致和状态不一致。
- 展示差异所属单位、商家、支付账号、订单和当前处理状态。
- 每项差异必须确认并写明最终业务结果，包括成功、失败、退款、账外资金或继续调查，不能只补充说明后关闭。
- 对账可以将“结果未知”确认成成功或失败；人工确认必须提供凭证并由另一名有权限人员复核。
- 所有人工处理保留操作人、处理时间、处理原因和处理前后结果。

### 4.5 机器人管理

#### 机器人实例

- 总部可以创建总部自营支付机器人；代理商可以创建本代理商支付机器人。
- 每个机器人设置名称、识别编码、Telegram 连接信息和可用功能；实际支付账号和通道由群组绑定的商家支付方案确定。
- 可用功能包括创建支付订单、提交支付批次、订单查询、余额查询、获取回单、支付统计、C2C 订单支付、付款结果通知、订单申诉和 C2C 日报。
- 可以分别设置“创建支付订单是否需要二次确认”和“提交批次是否需要二次确认”。
- 支持启用、停用、开始运行和暂停运行，并展示当前连接状态。
- 机器人停用或暂停运行后，不再接收群内指令，也不再执行新的群内业务。

#### 群组绑定

- 机器人超级管理员可以在 Telegram 群内发起绑定，也可以在后台完成绑定。
- 一个支付机器人可以绑定多个群组，每个群组只绑定一个所属单位下的一个商家。
- 绑定时指定商家和群内支付场景，并设置群组可使用的功能、是否允许群内创建支付订单、单笔金额上限和启停状态。
- 群内订单根据该支付场景匹配商家的支付方案，不能使用其他业务场景的账号和通道。
- 群组只能使用机器人已经开通的功能，不能通过群组配置增加机器人没有的功能。
- 总部自营群组只能绑定总部自营商家；代理商群组只能绑定本代理商商家。
- 群组停用后立即停止新的群内操作，已提交订单继续查询最终结果。

#### 群组成员

- 按 Telegram 用户编号添加群成员，角色分为群管理员和操作员。群成员是 Telegram 独立身份，只维护 Telegram 用户资料和群内权限，不要求绑定系统后台用户。
- 为成员单独分配创建支付订单、批次提交、订单查询、余额查询、获取回单、统计、申诉和日报等权限。
- 成员只能使用机器人和当前群组均已开通的功能。
- 群管理员负责本群日常业务，操作员只执行已分配的具体操作。
- 成员停用或移除后，群内操作权限立即失效。

#### 超级管理员

- 平台超级管理员由总部设置，可以管理全部机器人并绑定群组。
- 机器人超级管理员只管理指定机器人，可以为该机器人绑定商家群组。
- 超级管理员通过 Telegram 用户编号识别，不因修改用户名而失去身份。超级管理员是 Telegram 独立身份，只维护 Telegram 用户资料和管理范围，不要求绑定系统后台用户。
- 超级管理员停用后，不再允许新增或变更群组绑定。

#### 群内支付功能

- 群成员可以发送四行支付信息创建支付宝转账订单，依次为商户订单号、金额、收款姓名和支付宝收款账号。
- 一条消息可以包含一笔或多笔支付信息，多笔信息按每四行一笔识别并逐笔校验；错误项单独说明原因，正确项可以继续确认和创建。
- 机器人检查群组绑定、成员权限、下单开关、单笔限额、信息完整性和订单是否重复。
- 需要二次确认时，机器人先展示通过校验的订单笔数、总金额和收款信息，由操作人员点击确认下单或取消；确认时重新检查机器人、群组、成员、商家和权限状态。
- 订单受理后进入待提交状态，群内可以查询订单或在提交前作废订单。
- 群成员可以发起提交批次；需要二次确认时，机器人展示待提交笔数、批次组数和总金额后再提交。
- 机器人将支付成功、失败、部分成功和失败原因回复到原业务消息；成功订单可以直接获取回单。
- 群内支持查询订单或批次、查询余额、查看今日支付统计、获取回单、发起 C2C 申诉和查看 C2C 日报。

#### C2C 订单支付

- C2C 买币订单满足付款条件后，系统核对订单金额、收款账号、收款姓名和实名信息。
- 信息一致时，系统通过商家绑定的支付机器人自动创建支付订单，并在群内通知。
- 实名不一致或需要人工复核时，机器人将订单推送到商家群，由有权限人员选择确认下单或取消订单。
- 支付成功后，系统进入“已付款，待平台确认”，继续向交易平台确认已付款；确认失败或超时时只重试平台确认，不重新付款。
- 支持对满足条件的 C2C 订单发起申诉，并提供订单日报查询。

### 4.6 系统管理

- **所属单位**：总部新增、编辑、启用和停用代理商；“总部自营”为系统固定单位，不允许删除。
- **用户与角色**：总部管理全部用户，代理商管理本单位用户；可按商家和功能分配权限。
- **支付通道配置**：总部维护全平台可使用的支付方式和通道；各所属单位在支付账号中选择已经开通的通道。
- **自动任务**：查看订单获取、状态更新、支付结果查询、账单获取、对账和通知发送情况。
- **操作记录**：查询登录、权限变更、商家变更、支付审核、付款提交、人工处理和导出记录。
- **系统参数**：总部维护全平台公共参数，各所属单位只能查看与自身业务有关的内容。
- 代理商停用后不能新增商家、获取新订单或产生新的支付业务，历史记录继续保留查询。

## 六、业务流转

### 6.1 所属单位建立

1. 系统预设“总部自营”所属单位，总部无需新建即可开展自营业务。
2. 总部需要发展代理商时，在系统管理中新增代理商并填写基本资料。
3. 总部为代理商创建管理员并分配可使用的业务功能。
4. 代理商启用后，可以管理本单位的商家、支付账号、订单和支付机器人。
5. 总部可以随时查看代理商经营数据，也可以按权限协助处理业务。

### 6.2 新建商家

1. 操作人员进入“商家”，点击新建。
2. 总部操作时选择所属单位，默认为“总部自营”；代理商操作时自动归属本代理商。
3. 填写商家名称、编码、联系人和经营资料。
4. 选择币安或欧易，只能选择其中一个。
5. 填写所选平台的商家账号和连接资料。
6. 检查连接正常后保存，商家进入“待启用”或“正常”状态。
7. 为商家配置本单位的支付方案，绑定支付机器人群组和通知规则。
8. 商家可以先启用订单获取；没有可用支付方案时，订单仍可获取，但自动付款不能启用，新订单保持“待付款”。人员手工发起支付后仍无方案时，支付订单进入“待配置”。
9. 至少存在一条满足 C2C 自动付款条件的方案并检查通过后，才能启用自动付款。

### 6.3 订单获取

1. 系统按每个商家选择的交易平台定时获取新的 C2C 买币订单和状态变化；本期忽略卖币订单，不生成本地业务待办。
2. 首次发现的订单创建为商家订单，重复发现时只更新订单状态。
3. 订单自动继承商家的所属单位，不能转移到其他单位。
4. 新订单和重要状态变化显示在工作台，并按规则发送机器人群组通知。
5. 获取失败、状态不一致或订单争议时，订单标记为异常并进入待办。
6. 运营人员可以对单笔订单或指定时间范围重新获取。

### 6.4 买币订单

1. 系统获取买币订单后，订单进入待付款。
2. 系统读取平台订单号、金额、币种、收款方式、收款账号、收款姓名和付款截止时间。商家启用自动付款时系统自动创建支付订单；未启用时订单保持“待付款”，由有权限人员在后台或机器人群确认创建。
3. 系统匹配并锁定“支付账号 + 支付通道”，同时占用额度；没有可用方案时支付订单进入“待配置”，商家订单保持“待付款”。
4. 需要审核时，由有权限人员完成审核；不需要审核或审核通过后，支付订单进入“待提交”。
5. 正式付款前，系统再次向交易平台核对订单仍可付款，且金额、收款资料和付款截止时间没有变化，同时重新检查权限、支付账号、支付通道、余额和额度。
6. 平台订单已取消、已过期或收款资料变化时停止付款并取消尚未提交的支付订单，释放额度，商家订单进入对应状态或异常待办。
7. 付款提交后，商家订单进入“支付处理中”；付款明确失败且未扣款时释放额度，订单仍在有效期内可重新匹配方案并再次审核，已失效则结束付款流程。
8. 付款结果未知时保留额度占用，只查询、对账或人工核实原付款，不允许更换账号或通道再次付款。
9. 付款成功后，商家订单进入“已付款待平台确认”，系统向币安或欧易确认已付款。平台确认失败或超时时只重试该确认动作，不重新付款；自动确认在付款时限内仍未成功时，转人工在交易平台完成确认，系统重新获取平台状态进行核实。
10. 平台确认已付款后，订单进入“待放币”；交易平台确认对方放币后，订单完成。
11. 已经付款但平台订单取消、过期、对方未放币或状态冲突时，订单进入“资金异常”，通过平台申诉、催办放币、退款追踪或人工处理直至资金或数字资产结果明确，不得直接关闭订单。

### 6.5 卖币业务扩展预留

1. 本期不获取、不展示、不处理卖币订单，不提供确认收款和放币操作，也不开放相关机器人命令。
2. 商家订单保留“买币/卖币”方向，交易平台接入保留按能力启用不同方向的扩展位置，卖币能力默认关闭。
3. 后续启用卖币前，单独增加卖币订单状态、收款核对记录、到账流水匹配、放币审核、平台放币结果和争议处理，不复用买币付款状态代替。
4. 后续收款核对必须同时核对收款账号、金额、付款人、渠道流水号、付款时间和款项占用关系；无法唯一匹配时必须人工确认，未确认到账不得放币。
5. 卖币扩展不得改变现有买币支付订单、支付方案、批次和对账规则。

### 6.6 单笔支付

1. 支付订单可以来源于 C2C 买币订单或机器人手工支付；退款订单必须关联原成功支付订单。每类来源按所属单位、商家、来源和原业务编号防重。
2. 系统读取业务场景、收款方式、金额、币种、付款或退款方向和即时或批量要求。
3. 系统只从该商家的支付方案中筛选同时满足条件的支付账号和支付通道。
4. 系统按主用、备用顺序和分配比例选中一条方案，锁定账号与通道并占用额度。
5. 需要审核的支付订单先由有权限人员审核；审核时展示本次选中的账号和通道。
6. 正式提交前重新检查来源业务、操作权限、收款信息、账号和通道状态、余额、额度及使用时段；C2C 买币订单还必须重新检查平台订单状态和付款截止时间。
7. 检查通过后，支付订单从“待提交”进入“提交中”；支付通道受理后进入“处理中”，系统持续获取处理结果。
8. 提交前失效或支付通道明确返回未受理、未扣款时，释放额度并可以重新匹配备用方案；重新匹配后按规则再次审核。
9. 已受理、处理中或结果未知时，不得更换账号或通道，只能查询、对账或人工核实原支付结果。
10. 明确失败时释放占用额度；成功时将占用额度记为实际使用；结果未知时继续占用，直至确认成功或失败。
11. 最终结果同步更新支付订单、来源业务、支付账号额度、商家使用额度和方案使用情况。
12. 支付订单只有在尚未向通道提交时才能取消或审核拒绝，取消后立即释放额度。C2C 买币订单仍有效时保持“待付款”，后续通过“恢复支付”重新核对并复用原支付订单；机器人手工支付取消后永久作废该商户订单号；退款取消后可使用新的退款申请号再次发起。

### 6.7 批量付款

1. 财务人员选择符合条件的支付订单，或由系统按预设条件自动组批。
2. 系统按所属单位、商家、已经锁定的支付账号、支付通道和币种分别生成批次，任一条件不同都不能进入同一批次。
3. 系统检查每笔订单的付款截止时间。预计不能在截止前完成的订单不得等待组批；尚未提交时释放原批量方案占用，将执行方式改为即时，重新匹配即时方案并按规则重新审核。没有即时方案时进入人工待办，由人员在截止前补充即时方案并在系统内完成支付，或者停止付款。
4. 提交前重新核对操作权限、总笔数、总金额、每笔订单状态、来源业务状态、收款资料、付款截止时间、账号与通道状态、余额和额度。
5. 检查通过后批次进入“提交中”，支付通道受理后进入“处理中”，并持续获取每笔明细结果。
6. 只要存在处理中明细，批次保持“处理中”；存在无法确认的明细时，批次进入“结果未知”。
7. 全部明细均有最终结果后：全部成功记为“全部成功”，成功与失败并存记为“部分成功”，全部失败记为“全部失败”。
8. 成功明细永久保留原结果；只有明确失败、确认未扣款且仍符合付款条件的明细可以重新处理，处理中或结果未知的明细不得再次付款。
9. 批次审核拒绝或提交前取消时释放批次锁定，未失效的明细返回“待提交”；已经取消、过期或资料变化的明细退出批次并进入对应状态或异常待办。

### 6.8 对账处理

1. 系统按支付账号获取指定日期的账单。
2. 将账单与系统支付订单按业务编号、渠道流水号、支付账号、金额、币种、状态和业务日期进行核对。
3. 信息一致的记录标记为已对账。
4. 缺少记录、金额不一致或状态不一致时生成对账差异。
5. 系统有记录但账单无记录时继续获取账单或查询原支付；账单有记录但系统无记录时建立账外资金差异，禁止自动关联不确定订单。
6. 金额或状态不一致时，财务人员核对渠道凭证，并确认支付订单最终为成功、失败、退款或继续调查。
7. 对“结果未知”的支付订单，账单可以作为最终确认依据；账单仍无法确认时，由一名财务人员提交凭证和处理结论，另一名有权限人员复核后终结。
8. 差异只有在形成明确业务结论并同步更新相关订单、额度和资金记录后才能关闭，全部处理过程保留记录。

### 6.9 退款处理

1. 退款必须从原成功支付订单或已确认的资金异常发起；每次退款申请生成独立退款申请号，并记录原支付订单、原渠道流水和退款原因。
2. 系统检查可退款金额；累计成功退款金额与处理中退款金额之和不得超过原成功支付金额。
3. 退款按商家“退款”支付方案选择账号和通道，需要审核时由有权限人员审核。
4. 正式提交前重新检查退款权限、原支付状态、剩余可退金额、退款账号、通道、余额和额度。
5. 退款提交、查询、结果未知、对账和额度处理遵循单笔支付规则，重复操作不得产生第二笔退款。
6. 退款成功后更新原支付订单的已退款金额；全额退回时原支付订单标记为“已退款”，部分退款时保留“成功”并展示累计退款金额。
7. 退款失败或结果未知时不得增加已退款金额；结果未知必须先查询和对账，确认失败后才允许重新发起。

### 6.10 支付机器人开通

1. 总部或代理商在本单位下创建支付机器人并设置可用功能。
2. 根据业务需要设置创建支付订单和批次提交是否需要二次确认。
3. 启用机器人并开始运行。
4. 为机器人设置超级管理员，由超级管理员将 Telegram 群组绑定到指定商家。
5. 为群组选择商家和群内支付场景，并设置可用功能、创建订单开关和单笔限额。
6. 添加群组成员，分别设置群管理员或操作员角色及具体权限。
7. 完成后，群成员可以在授权范围内执行支付和查询操作。

### 6.11 群内创建支付订单

1. 有权限的群成员按四行格式发送商户订单号、金额、收款姓名和支付宝收款账号；商户订单号在当前所属单位、商家和机器人手工支付来源内唯一。
2. 机器人根据群组绑定的商家和“机器人付款”场景，匹配支付宝批量支付方案。
3. 机器人按每四行一笔独立检查商家归属、群组配置、成员权限、订单格式、单笔限额和重复订单；错误项单独返回原因，正确项继续处理。
4. 检查通过后，机器人只汇总正确项的订单笔数、总金额和收款信息，并同时列出未通过项目。
5. 需要确认时，由操作人员点击“确认下单”；确认时重新检查机器人、群组、成员、商家和权限状态。不需要确认时直接创建通过校验的支付订单。
6. 订单锁定具体的支付账号和批量支付通道后进入待提交状态，并在原消息下提供查询和作废操作。
7. 操作人员发送提交批次指令，机器人只汇总当前群组绑定商家下，所属单位、商家、支付账号、支付通道和币种均相同的待提交订单。
8. 需要确认时，由操作人员核对批次笔数和总金额后点击“确认提交”；系统再次鉴权并执行批次提交前复核。
9. 系统提交支付批次，并将成功、失败、部分成功及失败原因回复到原消息。
10. 成功订单可以在群内查询并获取回单。

### 6.12 C2C 订单机器人支付

1. 系统获取需要付款的 C2C 买币订单，并读取收款账号、收款姓名和实名资料。
2. 系统核对订单金额、交易方向、收款信息和实名结果。
3. 信息一致且商家已启用自动付款时自动创建支付订单，并在商家群通知“已自动创建”。
4. 未启用自动付款、实名不一致或需要人工确认时，将订单推送到商家群并展示确认付款和暂不付款按钮；选择暂不付款不会取消交易平台订单，商家订单继续保持“待付款”。
5. 操作人员确认前，系统重新检查机器人、群组、成员、商家和权限，并再次核对平台订单、收款信息和付款截止时间是否发生变化。
6. 支付成功后，商家订单进入“已付款待平台确认”，系统向币安或欧易确认已付款，并在原群组消息下反馈结果。
7. 平台确认失败或超时时只重试平台确认，不重新付款；订单保持“已付款待平台确认”并进入待办。
8. 已付款后平台订单取消、过期或对方未放币时进入“资金异常”，由申诉、退款追踪或人工处理收口。

### 6.13 异常处理

1. 订单、支付、对账或通知出现异常时，在工作台形成待办提醒。
2. 操作人员从待办直接进入对应订单、支付或对账页面。
3. 处理人员查看来源业务、支付尝试、渠道结果、账单、平台状态和最新处理记录，选择重新查询、对账、发起申诉、追踪退款或转交处理。
4. 涉及付款结果未知时，只能查询、对账或人工核实原付款，不能重新付款；结果明确前额度继续占用。
5. 已付款但尚未完成平台确认时，只能重试平台确认或转人工在交易平台确认后重新获取状态；已付款但订单取消、过期或未放币时，必须进入资金异常处理。
6. 只有明确未受理、未扣款且来源业务仍允许付款时，才能释放额度并重新匹配支付方案。
7. 人工确认资金最终结果必须填写原因并上传凭证，由另一名有权限人员复核；人工修改状态不能覆盖支付通道或账单已经确认的资金事实。
8. 处理完成并形成明确业务结论后关闭待办，保留处理人员、时间、原因、凭证和前后结果。

## 七、统一业务规则

1. 总部自营与代理商拥有相同的商家、订单、支付、对账和支付机器人经营功能。
2. 总部可以管理全部所属单位，同时直接管理总部自营的商家和支付账号。
3. 一个商家只能绑定币安或欧易其中一个平台，不能同时绑定两个平台。
4. 同一经营主体跨平台经营时，必须建立两个独立商家。
5. 商家的交易平台创建后不可修改，所属单位不可随意转移。
6. 商家只能绑定本所属单位的支付账号、支付机器人和群组。
7. 代理商只能查看和操作本单位数据，不得查看其他代理商或总部自营数据。
8. 重复获取同一平台订单时不得产生重复商家订单。
9. 重复点击、重复提交或系统重复处理时不得产生重复付款。
10. 支付结果未知时必须先确认原付款结果，不能直接再次付款或更换通道付款。
11. 批量付款部分成功时，只能重新处理已经明确失败的明细。
12. 商家、订单、支付订单和批量付款不直接删除，只能停用、取消、归档或标记异常。
13. 付款审核、批次提交、人工改动订单、重新付款和关闭异常必须保留完整操作记录。
14. 机器人、群组和成员权限同时有效时，群内操作才允许执行；任一层级未启用时立即拒绝新的操作。
15. 群内创建支付订单和提交批次是否需要二次确认，由机器人实例统一设置。
16. 群组只允许使用绑定商家的支付账号或通道，不能跨所属单位创建支付订单。
17. 用户、商家、支付账号、机器人或群组停用后，新的业务操作必须立即停止。
18. 商家订单只能使用该商家已启用的支付方案，每条方案必须明确到一个支付账号和该账号下的一个支付通道。
19. 支付订单提交前必须锁定账号和通道；已受理、处理中或结果未知时不得切换支付组合重新付款。
20. 不同所属单位、商家、支付账号、支付通道或币种的订单必须分别组批，不得混入同一个支付批次。
21. 商家支付方案的变更只影响尚未锁定的新订单，不改变已经锁定或已经提交订单的支付账号和通道。
22. C2C 买币付款、机器人手工支付和退款分别使用独立来源类型和防重编号，同一业务意图只能产生一笔有效支付订单。
23. 正式支付和批次提交前必须重新检查权限、来源业务、收款资料、付款时限、账号、通道、余额和额度，审核通过不能代替提交前复核。
24. 明确失败且未扣款时释放占用额度；成功时转为实际使用额度；结果未知时继续占用直到最终确认。
25. 付款成功后确认交易平台已付款失败，只能重试平台确认，不得重新付款。
26. 已付款但交易平台订单取消、过期或未放币时必须进入资金异常，不得直接标记普通取消、过期或关闭。
27. 对账差异和资金异常只有形成明确业务结论并同步相关订单及额度后才能关闭；人工确认资金结果必须双人复核。
28. 批次还有处理中或结果未知明细时不能标记部分成功；部分成功只适用于全部明细均已结束且成功、失败同时存在的情况。
29. 机器人最终确认创建订单或提交批次时必须重新鉴权；多笔消息逐笔校验，错误项不阻断正确项。
30. 本期只开放 C2C 买币付款。卖币所需的订单方向和平台能力保留扩展位置，但相关获取、页面、任务、收款核对、放币和机器人操作保持关闭。
31. 支付订单和批次只有在尚未提交时才可取消；取消或审核拒绝必须释放额度及批次锁定，并按来源决定恢复原 C2C 付款、永久作废机器人商户订单号或允许新退款申请。
32. 通知发送失败只重试通知并形成待办，不改变已经确认的订单或资金结果，也不能触发重新付款。

## 八、本期业务闭环验收

1. 没有支付方案时订单可以正常获取，自动付款不能启用，支付订单进入“待配置”；补充方案后可以执行“重新匹配”继续处理。
2. C2C 买币订单在正式付款前被取消、过期或修改收款资料时不会付款，已占用额度会正确释放。
3. 同一 C2C 平台订单、机器人商户订单号或退款业务被重复操作时，不会产生第二笔有效支付订单或第二次资金提交。
4. 支付通道超时后订单进入“结果未知”，只能查询、对账或人工双人确认，不能换账号或通道重新付款。
5. 支付成功但平台确认失败时，订单保持“已付款待平台确认”，系统只重试平台确认。
6. 已付款后平台订单取消、过期或未放币时，订单进入资金异常并可以继续申诉、催办或追踪退款。
7. 批次按所属单位、商家、账号、通道和币种隔离；存在处理中或结果未知明细时不会提前判定部分成功。
8. 机器人多笔输入中，错误项有独立原因，正确项可以继续创建；最终确认时权限失效会立即拒绝。
9. 对账能够将结果未知收口为成功或失败；无法由账单确认时，可以通过财务提交凭证和另一人复核形成最终结果。
10. 卖币相关菜单、任务和操作在本期不可用，未来增加卖币流程时不改变现有买币支付订单和批次结果。
